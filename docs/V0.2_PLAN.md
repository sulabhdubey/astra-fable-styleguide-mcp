# v0.2.0 implementation plan

This plan turns the [build specification](../BUILD_SPEC.md), master handover, and pinned project goal into reviewable increments. v0.1.0 remains the released public baseline. A merged change on `main` is development evidence, not a new release.

## Scope and current evidence

- **Done:** Public v0.1.0 on a pinned Vercel production branch; eight read/compliance tools; Codex CLI and Cursor CLI coding-agent trials; GitHub branch protection and client documentation.
- **Done on main, unreleased:** Located deterministic CSS findings with explicit coverage limits; a TypeScript client tested against a local official MCP server and the live v0.1.0 endpoint; a hash-verified snapshot of all 25 v0.1.0 `/spec` JSON files and deterministic snapshot comparison.
- **Next:** Better MCP discovery/onboarding, useful deterministic token/style checks beyond literals, a successful independent provider-backed Astra/Fable candidate on a free or explicitly approved path, an actual reviewed v0.2.0 `/spec` candidate, and a second immutable snapshot. The local Ollama adapter and process-local governance view are development increments; neither establishes release-grade governance.

## Architecture and schema

`/spec` remains canonical. The historical snapshot index is derivative and hash verified. The existing eight MCP tool names and argument names remain stable; new result fields are additive. The TypeScript client reads the public MCP and owns no business rules. Public requests remain read oriented and stateless. Provider-backed generation remains optional, with deterministic mock coverage in CI.

The v0.2.0 design changes must be proposed, reviewed, deterministically evaluated, and tied to an exact candidate SHA-256 before `/spec` is changed. Capture the candidate's `/spec` as a new immutable snapshot only after its design delta is reviewed. The `0.1.0 → 0.2.0` tool result must then report real token/component/rule changes from both snapshots. Generated JSON, CSS, TypeScript, and docs must be reproduced from that candidate.

## Delivery sequence

1. Publish tested Codex/Cursor onboarding examples and a machine-readable discovery path. Verify discovery with actual clients.
2. Expand compliance for practical token/style cases with fixtures from the two agent trials. Keep `not_checked`, truncation, and coverage limits explicit; stage component and accessibility analysis separately.
3. Run one genuinely independent provider-backed Astra/Fable proposal and cross-review cycle without an unexpected paid call. Prove provider failure cannot create an approved candidate or change `/spec`.
4. Expose proposal, conflict, round, candidate-hash, approval, and readiness state to authorized operators. Label current in-memory state as prototype behavior until identity and durable audit records are designed and verified; do not claim a mature multi-user workflow from it.
5. Review and merge a substantive v0.2.0 canonical spec candidate and capture its immutable snapshot. Verify meaningful `0.1.0 → 0.2.0` results, including breaking/deprecation notes where applicable.
6. Run connected CI, Docker, audit, reproducibility, MCP contract, security, and rendered client checks. Present the exact candidate commit, hashes, diff, evidence, and release notes for human approval. Only then dispatch the manual release gate with that SHA, create the immutable tag, and switch the public deployment.
7. After live verification, prepare a concise reply to Tibo's original post with the demo, repository, and accurate maturity label. Post only after the user's approval.

## Compatibility, migration, and deployment

Keep v0.1.0 online throughout development. Existing clients must still call the same eight tools. Validate both legacy `initialize` and 2026 `server/discover` against the candidate. The new compliance fields are optional in the TypeScript client while v0.1.0 is live. A v0.2.0 spec version bump requires regenerated artifacts and a new snapshot; never edit the v0.1.0 tag or snapshot. Production secrets remain absent from the public read-only service, and no mutation or release tool is enabled there. The release workflow is manual and binds approval to the exact checkout SHA.

## Acceptance evidence

- At least two real coding-agent examples retrieve rules before implementation and record honest compliance results.
- A programmatic client connects to the public MCP; all eight v0.1.0 tools remain callable with their existing arguments.
- Deterministic fixtures catch useful real-world violations and state what was not checked.
- A genuinely independent provider-backed cycle produces a candidate only after both directions of review and deterministic evaluation; no provider call is required in CI.
- The two immutable snapshots yield a meaningful machine-readable version diff.
- Public production exposes no governed mutation or release tools; approval identity and audit limitations are documented and tested before stronger governance claims.
- `pnpm install --frozen-lockfile`, lint, typecheck, test, validate, build, reproducibility, audit, MCP smoke, and Docker pass on the exact release candidate. Generated artifacts and release evidence are inspectable.
- A human approves the exact candidate SHA and authorizes publication and any public outreach.

## Cost and risk controls

Use deterministic local tests first and one bounded provider-backed trial only when a free path is confirmed or the user approves a specific charge. Recheck live Codex usage after substantial work. Avoid a database until multi-user governance needs and durability semantics are defined. Do not treat a passing text scanner as a complete accessibility or UI review.
